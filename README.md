# FIARS — Fault Resolution Intelligence Platform

An offline fault-diagnosis tool for data-centre hardware maintenance. Paste a raw
fault ticket, get back structured fields, a formatted report, the on-site diagnostic
commands for that fault category, and a ranked answer to the question that actually
matters on the floor: **what fixed this last time?**

Pure Python standard library and SQLite. No pip install, no services, no network.
`python server.py` and it runs.

---

## The data in this repository is synthetic

This is the public portfolio build. Every knowledge-base entry, error code, server
model, serial number, rack location and historical case in it was generated for this
repository and describes hardware that does not exist.

- The fictional platform family is defined in [`scripts/synthetic_spec.py`](scripts/synthetic_spec.py).
- The dataset is generated by [`scripts/generate_synthetic_kb.py`](scripts/generate_synthetic_kb.py),
  deterministically. Delete `kb_content/*.json`, re-run it, and `git diff` comes back
  empty — which is how you can check that the committed data really is the generated data.
- Open industry standards are deliberately kept real, because inventing them would make
  the tool incoherent to anyone who works on this hardware: SMART attribute IDs,
  IPMI/SEL terminology, ECC/UCE, MCE, IERR/CATERR, UPI, PCIe AER, Xid as a log
  signature class, and public tooling names (`ipmitool`, `smartctl`, `nvme-cli`,
  `dmidecode`, `edac-util`). Every *value* those standards carry here — specific Xid
  numbers, SEL event codes, rail names, platform SKUs — is fabricated.

The architecture, the parsing, the retrieval, the ranking and the report generation are
the real thing. Only the data is invented.

## What it does

**1. Ticket parser.** Paste a raw fault block — a single fault, several fault blocks, or
a whole dispatch table copied out of a webmail client — and get parsed structured fields,
a generated report, category-appropriate diagnostic commands and log-collection paths,
and a ranked "similar past cases" panel.

The parser handles the awkward parts of real ticket exports: bilingual `中文/English`
field labels, tab-delimited pastes with no colons at all, values containing colons
(an IPv6 address will otherwise split in the wrong place), Outlook pastes that emit a
blank line after every table cell, and one ticket that covers two parts on the same host.

**2. Checklist and attestation forms.** Auto-fills an inspection checklist from the
parsed ticket — server info, category-aware pre-checked items, hot-swap versus
power-off guidance — and downloads a landscape A4 PDF directly, with no print dialog.
Generated client-side by jsPDF, vendored locally rather than pulled from a CDN, so the
whole application stays offline-capable.

**3. Knowledge base search.** SQLite FTS5 with synonym expansion, error-code extraction
and category bias. A query for "PSU" also matches entries worded as "power supply".

**4. Case ranking.** Retrieved cases are weighted by similarity × recency × fix-success
and aggregated into confidence-scored root causes and resolutions. Details below.

**5. Paginated case history.** Server-side pagination, search and sort.

**6. Raw dump repository.** Upload fault logs, exports, emails or screenshots. Text is
extracted, indexed and searchable, and a dump can be promoted into a knowledge entry.
Sample dumps are in [`samples/`](samples/).

    python server.py          # or double-click start.bat on Windows

The server initialises the database, loads the knowledge base, runs a self-test and
opens `http://127.0.0.1:5000`.

application, but a case history belongs to whoever is running it:

## Three design decisions worth explaining

### Zero dependencies was a constraint, not an aesthetic

This runs on maintenance workstations inside data halls. Those machines have no
outbound internet, locked-down software installation, and an engineer holding a ticket
who needs an answer now. Anything requiring `pip install` at the point of use is not a
tool, it is a support request.

So the backend is Python standard library and SQLite — `http.server`, `sqlite3`,
`json`, `re`. The frontend is one HTML file with jsPDF vendored into `vendor/` and
served from a hardcoded two-file allow-list, not a general static handler, so there is
no path-traversal surface. The requirements file exists and is empty on purpose.

The constraint pays off in the demo too: clone the repository, run one command, and
there is a populated knowledge base to search. No setup step, no seeding, no
credentials.

### FTS5 with synonym expansion, chosen over embeddings

The obvious modern answer for "find similar past faults" is sentence-transformers plus
a vector index. `all-MiniLM-L6-v2` is 384 dimensions and about 80 MB, and it would
work. It was evaluated and rejected. The reasons, in order of weight:

**It breaks the deployment constraint.** PyTorch, transformers and FAISS turn a
zero-install tool into a multi-gigabyte environment on a machine that cannot reach PyPI.
That alone decides it.

**Fault text is not the kind of text embeddings win on.** Embeddings earn their cost on
paraphrase — where two passages mean the same thing in different words. Fault tickets
are the opposite: short, code-dense, and carrying most of their signal in exact tokens.
`Xid 212`, `SMART_197`, `RAIL_PVDDQ_AB_CPU0_FAULT` and `CPU_IERR` are identifiers.
BM25 matches them exactly; an embedding blurs them toward whatever else it thinks is
semantically nearby. The vocabulary problem that remains is narrow and closed — "disk"
versus "HDD" versus "drive", "PSU" versus "power supply" — and a hand-maintained
synonym map covers it directly, in about forty lines, with no inference step.

So [`fiars/smart_search.py`](fiars/smart_search.py) runs four strategies over FTS5 and
fuses them:

1. **Error-code extraction.** Regex out the identifiers first and query them alone.
   This is the highest-precision signal available and it gets the highest weight.
2. **Synonym expansion** over component terms only — nine closed groups. Deliberately
   not a general thesaurus: expanding generic words is how a search like this starts
   returning everything.
3. **Category inference**, with a 3× boost for an exact category match. Knowing a fault
   is Storage rather than Memory prunes more of the result space than any amount of
   semantic similarity.
4. **Raw token query** as the fallback.

Results are merged with reciprocal-rank fusion — `weight / (1 + rank)`, where earlier
strategies carry more weight — so a document found by two strategies outranks one found
by either alone.

The honest summary: for this corpus, a lexical index with a small curated synonym layer
returns better results than embeddings would, costs nothing to ship, and has no failure
mode that requires debugging a model. The version of this project that shipped
embeddings would have been the less thoughtful one.

### The ranking formula

Retrieval gets you candidate cases. Ranking answers the question the engineer is
actually asking, which is not "what looks similar" but "what worked". The two come
apart constantly: the most textually similar case might be one where the engineer
swapped a part, closed the ticket, and the fault came back a week later.

Each retrieved case gets a weight ([`fiars/recommend.py`](fiars/recommend.py)):

```
weight_i = similarity_i × recency_i × success_i

  similarity_i  rank-decay over BM25 retrieval position, in [0,1]
  recency_i     exp(-age_days / 365)
  success_i     1.0 if the fix held, else 0.25
```

**Similarity** is rank-decayed rather than raw BM25, because FTS5's score scale is not
meaningfully comparable to the other two terms — only the ordering is trustworthy.

**Recency** decays exponentially with a one-year time constant. Firmware levels change,
batches of parts age out, procedures get revised. A fix from three years ago is weaker
evidence than the same fix from last month, and the decay says so continuously instead
of by an arbitrary cutoff.

**Fix-success** is the part worth stealing. A recurrence within the follow-up window is
a fix that did not hold, so the case already carries its own label — no separate
feedback mechanism, no one grading anything. Failed fixes are not discarded, they are
downweighted to 0.25, because knowing that reseating usually fails for a given fault is
useful information.

Weights are then aggregated into buckets by outcome label and converted to confidence
with additive smoothing:

```
confidence = (bucket_weight + α) / (total_weight + α × (n_buckets + 1))     α = 0.5
```

The smoothing does two things. It stops a single matching case from returning 100%
confidence, which would be a lie. And the leftover mass appears explicitly as an
`Other` bucket — the model's own estimate of how much it does not know. A recommender
that cannot say "I am not sure" is worse than useless on a maintenance floor, because
it will be confidently wrong in front of someone holding a screwdriver.

Alongside this, raw ticket text is matched against the BMC error map, which resolves a
rail-fault signature to a power rail, its suspect components, and for memory rails the
specific DIMM slots that rail feeds. That is a lookup, not a ranking, and it runs
independently — deterministic hardware knowledge should not be diluted by statistics.

## Layout

```
server.py              stdlib HTTP server, routing, JSON API
fiars/
  parser.py            single and multi-block ticket parsing, field aliasing
  parser_table.py      dispatch-table parsing, Outlook paste repair, merge logic
  report.py            report generation
  diagnostics.py       per-category commands and log-collection paths
  smart_search.py      FTS5 multi-strategy search, synonym expansion
  recommend.py         similarity × recency × success ranking, KB pattern lookup
  db.py                schema, FTS5 tables, pagination
  extract.py           raw dump text extraction
  bulk_parse.py        bulk import
  config.py            local config with safe defaults
kb_content/            the synthetic dataset (JSON, committed)
scripts/               loaders + the dataset generator
samples/               synthetic raw dumps to upload
templates/index.html   the entire frontend
vendor/                jsPDF 2.5.2, jsPDF-autotable 3.8.4
tests/                 63 tests
```

## Configuration

Copy `config.json.example` to `config.json` to override the database path, backup
directory, engineer name, host and port. Safe to skip — the defaults work.

`allowed_origins` is empty by default. It exists for an optional browser-side helper
that can POST scraped fault blocks from a ticketing portal to this server; a site that
wants that sets its own portal origin there. `config.json` is untracked, so no origin
is ever committed.
